Moving the warehouse, and proving nothing moved

I moved seven tables of the warehouse behind my MLB model from SQLite into Snowflake, rebuilt them as a star schema with dbt, and checked every table against the original before trusting a single row. Everything ties out. The tests also caught three things the old database had never checked.

What was moved, and how

The MLB model runs on a 21-table SQLite warehouse fed by a nightly pipeline. I took the seven tables that form a clean star: one batting line per batter per game, pointing at the player, team, game, park and season. I did it to learn Snowflake and dbt properly, on data I know well enough to notice when a number is wrong.

The season check is the one I care about most. Its Snowflake side reads from the finished dbt fact table, not the raw copy, so it checks the transformation as well as the load. H+R+RBI was a generated column in SQLite that I deliberately didn’t copy. dbt rebuilds it, and it lands on the same totals.

Does the check have teeth? Before the real run I tested the script against a mock built from the same table definitions and deleted one row out of 720. Seven checks failed at once: row count, distinct keys, four column totals, and that season’s line. One dropped row can’t hide. Full reconciliation output →

The tests found what SQLite had been letting through

Snowflake accepts primary and foreign key syntax but only enforces NOT NULL, so in the new warehouse dbt tests do that job. Three relationship tests came back with results. None were migration errors. They were already true in the source, and SQLite never checked them because none of those columns had a foreign key.

Batter not in player table281 lines147 distinct players

A rename the dimension can’t represent. The A’s became ATH for 2025. The team table stores current abbreviations only, so every 2024 Oakland home game points at a code that no longer exists. That’s a textbook slowly changing dimension. The fix is to keep the history, each name valid for a date range.

All-Star rosters. AL and NL, team IDs 159 and 160.

Exhibition games. YOM and HAN line up with the Yomiuri Giants and Hanshin Tigers, MEM with Memphis (Triple-A), MTY with Monterrey. The other team IDs sit outside the range MLB uses for its 30 clubs. The 147 missing players are very likely these rosters. Foreign and minor-league players were never in an MLB player table.

Altogether that’s 276 of 157,853 batting lines, 0.17%, from games that aren’t regular season. That’s too few to move the model’s backtest, but the table has no game-type field to filter on, and it should.

PART
04

Four decisions, and one bug caught early

Land raw, transform in the warehouse. RAW keeps the source exactly as it was. If a cast goes wrong in staging, the original value is still one layer down.

Don’t migrate derived values. Rebuild them, then check. Copying total_runs and hrr would only prove the copy worked. Rebuilding them and reconciling proves the logic matches too.

Constraints become tests. That’s not a workaround. It’s where every finding in Part 03 came from.

A key pair, not a password. Snowflake is retiring password-only sign-ins for scripts. The scripts and dbt log in as a service user that has no password at all.

The bug. The first export let pandas infer column types from the data. In testing, a column that was entirely NULL came out as text, which would have broken the load into a numeric column. The export now takes every type from SQLite’s declared schema and fails loudly if a value doesn’t fit.

What this isn’t

  • Small. 177,812 rows, three seasons, one person, one afternoon. A production migration has live users, downstream reports to re-point and a cutover window. This had none of those.
  • A full reload, not incremental. Right for a one-time move. Keeping Snowflake in sync with the nightly pipeline would take incremental models and merges.
  • Inferred labels. The exhibition games are identified from abbreviations and ID ranges, not an official game-type field, which this table doesn’t have.
  • An open question. 2,731 games have no result row and sit in dim_game with an empty score. Postponements and unplayed games are the likely answer. I haven’t traced it yet.
  • Provisional cost. About 0.1 credits as first reported. Snowflake usage figures can lag up to 24 hours.

What was built

  • Parquet extract with types taken from the source schema
  • Snowflake stage, COPY INTO loads, a cost-capped warehouse and a key-pair service user
  • A dbt project: 7 staging views, 5 dimensions, 1 fact table, 29 tests
  • A reconciliation script that runs the same checks on both ends

What comes next
